# Frontend Architecture

Тут попробую развернуть идеи, которые стоят за архитектурой нашего фронтенда.  
Рассказывать буду, ссылаясь на MVVM и .NET WPF, так как, вроде, все тут с ним знакомы.

## WPF

В случае WPF и подобных ему фреймворков он достаточно четко делится на как минимум два слоя\*:

- **View** - декларативное описание UI с достаточно большим набором батареек, таких как различные list-view и хитроумные биндинги к модели.
- **ViewModel** - совокупность реактивных сущностей (ObservableCollection, INotifyPropertyChanged и пр.), которая отвечает за всю логику приложения, не относящуюся к интерфейсу.

\*_Про Model ниже._

```xml
<Window ...>
	<StackPanel>
		<!-- Двусторонний биндинг -->
		<TextBox Text="{Binding Search, UpdateSourceTrigger=PropertyChanged}" />
		<!-- Биндинг к коллекции объектов -->
		<ListBox ItemsSource="{Binding ItemsView}">
			<ListBox.ItemTemplate>
				<DataTemplate>
					<DockPanel>
						<TextBlock Text="{Binding Name}" Margin="2" />
					</DockPanel>
				</DataTemplate>
			</ListBox.ItemTemplate>
		</ListBox>
	</StackPanel>
</Window>
```

```csharp
public class ViewModel : ViewModelBase {
    // При изменении этой коллекции, view подписанный на нее перерисуется самостоятельно
	private ObservableCollection<Item> Items = new();
	public ICollectionView ItemsView => CollectionViewSource.GetDefaultView(Items);

    // То же самое тут
	private string search;
	public string Search {
		get => search;
		set {
			search = value;
			OnPropertyChanged();
		}
	}

	...
}
```

Ну и весь "секс" получается за счет того, что зависимость между этими двумя слоями направлена (преимущественно) в одну сторону: **View → ViewModel**, и ViewModel вообще не знает о View:

1. **View:** что-то (Command или в нашем случае двусторонний биндинг к Search) побуждает ViewModel к действию.
2. **ViewModel:** обращается к бэкенду, обрабатывает полученные данные и сохраняет их себе (бизнес-логика) в Items.
3. **View:** реактивно обновляет свой кусок благодаря подписке на свойство модели.

## Что в React?

В React этого нет!  
React представляет собой _исключительно_ слой View.

Причем слой View довольно скромный и императивный:

- Без биндингов - мы должны вручную вызывать коллбэки, чтобы что-то поменять в UI на уровне компонента:
  ```javascript
  let [value, setValue] = useState(0);
  ```
- Без готовых абстракций для работы с коллекциями.
- Без готовых компонентов вообще - у нас есть просто "голый" псевдо-DOM (JSX).
- Без инструментария для создания ViewModel и работы с бизнес-логикой - всё API, которое предоставляет React, предназначено исключительно для работы с UI.

А зачем тогда он такой нужен?

1. Реакт подарил миру невероятно простой и удобный способ декомпозиции интерфейса на компоненты.  
   Все, что уже было за десятилетия до него, он упростил до крайности: все компоненты - это просто функции `render(data) -> html`.  
   Компоненты можно пихать друг в друга до бесконечности, так же просто, как это можно делать с обычными функциями.

2. Так как компоненты - это просто JS-функции, мы можем писать _любой_ код вокруг и внутри компонентов, _любым_ удобным нам способом и абсолютно не ограничены в возможностях и способах решения задач.  
   _Для сравнения: попробуйте TreeView в WPF кастомизировать - охуеете._

3. Так как пункт 2 гарантирует нам бесконечное количество говнокода, раскрывается еще одна сильная сторона реакта:  
   Реакт прожует и отрендерит любой кошмар и говно. Как бы плохо разработчик ни написал приложение, как бы сильно ни текла память - реакт выдаст рабочий результат. Страшной ценой, но выдаст. Такой вот уроборос.

## ViewModel

Вернемся к ViewModel.

Так как реакт ничего не предлагает на этот счет, разработчики вынуждены закрывать этот вопрос самостоятельно.  
Если отбросить трагичный сценарий "лепить всё на хуках", есть много специализированных библиотек, например:

- [Redux Toolkit](https://redux-toolkit.js.org/)
- [MobX](https://mobx.js.org/)
- [Effector](https://effector.dev/) ⭐️

Обзора и сравнения этих библиотек не будет, главное, что любая из них лучше, чем ничего.

Почему? Потому что третий пункт из достоинств реакта даётся немалой ценой. Чтобы построить такой хитрый пайплайн преобразования данных в DOM, реакту всё-таки нужны некие механики и правила. Это приводит к тому, что пункт 2 не совсем правда: жизненный цикл реакта и его компонентов весьма своеобразен, запутан и от версии к версии меняется и развивается.  
Несколько примеров:

- В компонентах нет async/await.
- `useEffect(() => {}, [])` с 18-й версии вызывается всегда два раза.
- Хуки нельзя вызывать внутри блоков условных операторов.

И многое другое. Если разработчик выбирает писать большую часть своего кода в компонентах реакта, он становится его заложником, вместо того чтобы думать о высоком:

```tsx
export const MyComponent = () => {
  // Код внутри этой функции может быть выполнен неограниченное количество раз.
  // Задача React - не вызывать лишний раз мутацию DOM, а как он это делает - это уже его зона ответственности.

  // Если вы выбираете писать код своего приложения здесь,
  // вы должны постоянно думать о том, что в таком случае будет вашим приложением,
  // и загрязнять код бизнес-логики специализированным API React: React.memo, useCallback, useMemo, useEffect и т. д.
  return <div>...</div>;
};
```

Поэтому стремиться мы должны к чему-то такому:

```tsx
// src/model.ts

export const ViewModel = {
  // Делаем что хотим
  return {data, doSomething};
};

// src/view.tsx

// Некий слой адаптер, который берет на себя все сложности борьбы с реактом
import useModel from 'some-lib';

// Логика не связанная с UI теперь не зависит от реакта
export const View = () => {
  const model = useModel(ViewModel);
  return <div onClick={model.doSomething}>model.data</div>;
};
```

## Effector

Что предлагает Effector, чем он похож и отличается от .NET'овского ViewModel?

### ViewModel == Model.

Не зависимо от набора букв в выбранной архитектуре, под моделью зачастую подразумевают совокупность каких-то чистых и непорочных POJO-объектов, обзывая все это доменным слоем. Это оправдано для многих кейсов, но в случае фронтенда, где состояние приложения - это клубок запутанной хуйни, намазанной на интерфейс, это выходит боком.

Effector предлагает считать минимальными блоками для построения бизнес-логики не сами объекты и функции, а собственные реактивные примитивы. То есть, подобно тому, как React предлагает расширить язык своим DSL для написания интерфейсов (JSX), Effector расширяет язык своим DSL - реактивными Unit'ами. [Подробнее про это тут](https://github.com/borolgs/effector-intro).

И так как мы теперь конструируем доменный слой (Model) на реактивных примитивах, та роль, которую выполнял ViewModel, просто отпадает.

### Singleton

Effector _принципиально_ предлагает смотреть на модель как на глобальный синглтон. Тоже из-за специфики фронтенда - большая часть приложения активна всё время, пока открыта вкладка, поэтому мы принимаем, что время жизни большинства\* моделей стремится к бесконечности.

А если это синглтон - нет смысла в каком-то объекте или классе, и можно лупить все свойства модели на самом верхнем уровне.

И вместо такого:

```ts
// 1. объявление
class Model {
  public nestedModel: NestedModel;
  public data: any;
  public event() {
    // логика
    this.data = 42;
  }
}

// 2. инициализация, включая неизбежный DI(!)
const model = new Model(nestedModel);

// 3. использование
model.event();
```

мы делаем так:

```ts
// 1. объявление
const $data = createStore();
const event = createEvent();

// было в NestedModel
const $otherData = createStore();
const otherEvent = createEvent();

// 2. ????

// 3. использование - event - это просто функция.
event();
```

### Декларативное описание логики

А куда в предыдущем примере делся код метода `Model.event()`?

Вот же он:

```ts
// 1. объявление
const $data = createStore();
const event = createEvent();

// 2. логика
sample({
  clock: event,
  fn: () => 42,
  target: $data,
});

// 3. запуск
event();
```

Все описано по [той же ссылке](https://github.com/borolgs/effector-intro), не буду тут повторяться.

Но в общем идея в том, что мы не только вытащили модели на верхний уровень, но и саму логику, сами закономерности и связи - тоже вытащили на верхний уровень.

И если обозвать всё терминами MVVM, то это будет так:

```ts
// Model
const $data = createStore();
const event = createEvent();

// ViewModel
sample({
  clock: event,
  fn: () => 42,
  target: $data,
});

// View
event();
```

Все как бы то же самое, но благодаря дроблению на маленькие примитивы и простоте создания связей, мы получаем мощь, аналогичную тому, что нам дает React на View слое.
